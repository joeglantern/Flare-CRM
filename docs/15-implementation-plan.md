# 15 — Implementation Plan (backend first)

Each step ends with a runnable, tested state. Do not start a step before the previous one's
definition of done is met. IDs reference [01](01-requirements-traceability.md).

## Step 0 — Confirmations & access (client, 1–2 days in parallel)

- Yeastar edition/firmware, plan (Enterprise/Ultimate), API enabled, Client ID/Secret, PBX reachability (WireGuard or cloud), extension list ↔ agent list, recording enabled, trunk "Control Inbound Call" decision, Linkus SDK decision.
- Chat channel decision (WhatsApp Cloud API vs PBX messaging vs SMS) and credentials.
- Domain name, VPS provider, SMTP, off-site backup bucket, default country/currency/timezone.
- Read the client's PBX developer guide for exact call-control body fields; adjust `integrations/yeastar/client.ts` types.

## Step 1 — Monorepo & tooling skeleton

- pnpm workspace, `apps/api`, `packages/shared`, `packages/tsconfig`; ESLint 9 + Prettier + lefthook; Vitest config; CI workflow (lint/typecheck/test).
- `apps/api`: Fastify app factory (`app.ts`), `config/env.ts` (Zod), Pino logger with redaction, `plugins/security.ts` (helmet/cors/rate-limit/cookie/under-pressure), request context + request id, error handler with the standard error shape, `/health`, `/ready`.
- Dockerfile (multi-stage) + `compose.dev.yml` (postgres, valkey, seaweedfs, mailpit) + `compose.yml` skeleton.
- DoD: `pnpm dev` boots api against Docker deps; `GET /health` 200; CI green.

## Step 2 — Database foundation

- Prisma 7 + `@prisma/adapter-pg`; `prisma.config.ts`; init SQL (extensions `citext`, `pg_trgm`, `pgcrypto`; roles `crm_app`, `crm_migrate`, `crm_backup`).
- Schema for all entities in [05](05-data-model.md) (auth tables generated by Better Auth CLI and merged), hand-written SQL migrations for partial unique indexes, tsvector triggers, `CHECK`s, audit immutability trigger.
- Seed: dispositions, default pipeline/stages, settings, first admin from env.
- Testcontainers setup; factories.
- DoD: `prisma migrate deploy` clean on empty DB; seed idempotent; integration test harness runs one dummy test.

## Step 3 — Authentication & authorization (R-7.5)

- Better Auth instance + Fastify handler, Valkey secondary storage, admin + twoFactor + haveIBeenPwned plugins, access-control statement/roles in `packages/shared/permissions.ts`.
- `requireAuth`, `requirePermission`, startup route-guard assertion, visibility scope helper + repository `scope()` and ESLint rule `no-unscoped-prisma`.
- `modules/users`, `modules/teams` (admin CRUD, role change, deactivate, sessions revoke, avatar upload to storage), audit of auth events, email templates (verification, set password, reset).
- DoD: tests for sign-in, 2FA enforcement for managers, role change revoking sessions, 401/403 matrix, deactivated user cannot sign in.

## Step 4 — Core CRM entities (R-7.1, R-7.2, R-7.3, R-7.4)

Order: custom-fields → companies → contacts (phones/emails, dedupe, merge, search, timeline endpoint over Activity) → pipelines → deals (stage change + history) → leads (convert) → tasks (reminders via BullMQ delayed jobs) → notes → activity module (writer used by all of the above) → audit module (query API) → notifications module (in-app + preferences + email queue).

- DoD per entity: full route matrix tests, scope tests for each `agentVisibility` mode, activity + audit rows asserted, OpenAPI snapshot.

## Step 5 — Realtime layer

- `plugins/socket.ts` (handshake auth, rooms, Valkey adapter, per-user cap, session re-check), `packages/shared/socket-events.ts`, worker emitter, `entity:changed` broadcast from the event bus, `notification:new`.
- DoD: socket integration test (connect with cookie, receive `notification:new` after creating a task).

## Step 6 — Yeastar CTI (R-4.x) — the critical path

1. `integrations/yeastar/client.ts` + `token-manager.ts` against `FakeYeastarServer`.
2. `subscriber.ts` (leader lock, heartbeat, backoff, resubscribe) + `webhook-verify.ts` + `/webhooks/yeastar`.
3. `normalize.ts` (E.164, direction, ext→user cache maintained by user module events).
4. `call-state.ts` state machine + `modules/calls` (Call rows, dispositions, dial, control, link-contact, recording presign/stream).
5. `jobs/recording-download.ts`, `reconcile.ts` + cron, `pbx_events` archive + retention.
6. `GET /cti/capabilities|status`, `POST /cti/reconcile`, live-calls feed for managers, pop latency metric.
7. Fixture-driven tests for every scenario in [06 §15](06-yeastar-cti-integration.md); load test with 50 simultaneous ringing fixtures.

- DoD: against the client's real PBX in a staging extension: inbound pop ≤ 2 s measured, outbound click-to-call works, CDR logged with recording playable, reconnect + reconcile verified by pulling the network cable.

## Step 7 — Reports, import/export, web forms (R-7.6, R-7.1.5, R-7.2.1)

- SQL aggregates for call and pipeline reports (+ CSV export with injection-safe cells), streamed CSV import job with mapping & error report, public web form endpoint with origin allowlist/rate limit/honeypot.
- DoD: report numbers cross-checked against fixture data; 50k-row import under 60 s without memory growth.

## Step 8 — Infrastructure hardening & backups (R-8.x)

- Production `compose.yml` with all hardening flags, Caddyfile, bootstrap script, deploy script, backup container + restic, Uptime Kuma checks, metrics.
- Run the restore drill and record it.
- DoD: staging VPS deployed from CI; backup ran; restore drill passed; security headers verified with an external scanner; `pnpm audit`/Trivy clean.

## Step 9 — Frontend (Vite) — separate plan

- Auth screens, app shell with global CallPopup, contacts/companies/leads/deals(Kanban)/tasks(calendar)/notes, contact 360° timeline, calls list + disposition + recording player, inbox (P2), reports, admin (users, teams, pipelines, custom fields, dispositions, settings, PBX status, audit).
- Generated API types from OpenAPI; shared Zod schemas for forms; socket event typing from shared.

## Step 10 — Phase 2: chat

- `modules/messaging` + WhatsApp adapter (or Yeastar messaging), inbox UI, attachments, templates/24 h window, notifications.
- Backend status (2026-09-05): **done** — `ChannelAdapter` contract, WhatsApp Cloud API adapter (HMAC webhook verify, media up/download, templates, status receipts), conversations/messages/attachments API, `messaging.inbound`/`messaging.outbound` processors with retry classification, `conv:*` rooms, channel secrets AES-256-GCM at rest, integration tests against a fake Meta Graph API. Inbox UI lands with Step 9.

## Step 11 — Phase 3

- Email integration (IMAP/SMTP or Gmail/Microsoft Graph) into the timeline, PDF reports, automation rules (e.g. auto-task on missed call), SSO via Better Auth `sso` plugin, mobile-friendly PWA polish / native app decision.
